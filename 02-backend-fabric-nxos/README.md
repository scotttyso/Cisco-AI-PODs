# Subsystem 02 — Backend fabric (NX-OS / NDFC)

Deploys inventory-defined backend VXLAN EVPN fabrics through Nexus Dashboard
Fabric Controller. Site inventories are generated by the UI per environment;
pass the selected inventory explicitly with `-i`. `inventories/example/` is a
non-deployable reference only.

The inventory contract is `group_vars/backend_fabric_switches.yml` containing
`be_fabrics` and `be_fabric_features`, plus a parent group named
`backend_fabric_switches`. Its children are named
`backend_fabric_<fabric key>`. Each switch host has `be_switch` host variables
with `fabric_key`, `hostname`, `role`, `mgmt_ip`, `username`, and `pass_ref`;
`fabric_link_interfaces` and `breakout_commands` are optional. Fabric keys
must match `^[a-z][a-z0-9_]*$`. `be_fabric.location` is passed through when
present and omitted otherwise. Vault credentials use `vault_<pass_ref lower>`;
ND credentials use `vault_nd_admin_password`.

## Core connectivity gate

Before a template deployment, the read-only checker samples switch identity,
LLDP, and interface status. A fabric with a plan is checked against its
inventory-defined fabric name and a CSV plan covering every spine-to-leaf
pair. A fabric without a plan is checked using reciprocal LLDP spine-to-leaf
links and any declared `fabric_link_interfaces`. Exit codes remain 0 (pass),
1 (physical/input mismatch), and 2 (incomplete evidence or invalid input).
The sanitized JSON gate response is still the Ansible deployment interface.

Optional plans are supplied through `be_core_cabling_plans`, a mapping from
fabric key to CSV path. The checker CLI accepts repeated `--plan KEY=PATH`.
`be_core_sg2_plan` and `--sg2-plan PATH` remain backward-compatible aliases
for key `sg2`; do not set both forms for the same key. Planless fabrics are
valid. The legacy alias only applies when the inventory contains the `sg2`
key.

## Run

Create a per-environment vault from the inventory's tracked example, fill in
site credentials, and keep it gitignored with restrictive permissions. Run
from the repository root, selecting both the generated inventory and vault:

```bash
ansible-playbook \
  -i inventories/<environment>/inventory.yml \
  02-backend-fabric-nxos/automation/playbooks/02_backend_fabric.yml \
  -e aipod_vault_file=inventories/<environment>/group_vars/vault.yml
```

For the reference inventory, replace `<environment>` with `example` only for
syntax checking and offline tests; its placeholder credentials cannot deploy.
`aipod_vault_file` is optional when the inventory has
`group_vars/vault.yml`; the playbook otherwise resolves vault and fabric vars
relative to the selected `inventory_dir`. Override the fabric vars file with
`be_fabric_vars_file` if a generated inventory stores it elsewhere. To pass a
cabling plan to the role, for example:

```bash
ansible-playbook -i inventories/<environment>/inventory.yml \
  02-backend-fabric-nxos/automation/playbooks/02_backend_fabric.yml \
  -e aipod_vault_file=inventories/<environment>/group_vars/vault.yml \
  -e '{"be_core_cabling_plans":{"backend":"/path/to/backend-plan.csv"}}'
```

The checker also accepts an explicit `--vault-file` for direct runs. Keep all
vault values out of CLI arguments; only the path may be passed. The gate is
read-only, fresh on every run, and cannot be bypassed. A passing cable gate is
not sign-off for BGP, optics, traffic, or overall fabric health.
