reading the published CVD, and us when we forget what we did six months from

- Categories: `Added`, `Changed`, `Fixed`, `Removed`, `Security`, `Docs`.

### Added

- **2026-09-18 — `cluster.network.oob_subnet` — the third network an ND node touches.**
  An ND node sits on three networks: ND-MGMT, ND-DATA, and the out-of-band
  subnet carrying its CIMC. The inventory model only ever described the first
  two, so `network.cimc_subnet.<host>` warned on all three nodes that the CIMCs
  were "on neither the mgmt nor the data subnet" — a warning against the
  intended topology (lab decision D-011, CIMCs on Lab OOB-MGMT VLAN 10). The
  design was right and the model was incomplete.
  - `shared/lib/inventory.py`: `NetworkConfig` gains optional `oob_subnet` and
    `oob_gateway`, parsed and validated like any other subnet or address.
  - `schemas/nd-cluster.schema.json`: both fields added to `cluster.network`,
    neither in `required`. `additionalProperties: false` is retained, so typos
    such as `oob_subnett` are still rejected.
  - `automation/inventory/cluster.yaml`: declares `oob_subnet: 198.51.100.0/24`.
    `oob_gateway` is deliberately unset — that gateway is owned by the lab
    network team, and guessing it would put a fabricated address in the
    inventory.
  - `automation/scripts/precheck.py`: a CIMC on the declared OOB subnet now
    PASSes. Data-subnet placement still WARNs (§9 gotcha). A CIMC outside every
    declared subnet still WARNs, but now names the likely cause — a missing
    `oob_subnet` — rather than implying the CIMC is misplaced.
  - `automation/tests/test_inventory.py`: three tests covering omitted,
    declared, and malformed `oob_subnet`.
  - `automation/docs/precheck-checklist.md`: check description updated.

  **Effect on the live inventory:** pre-flight goes from `PASS=26 WARN=7` to
  `PASS=29 WARN=4`. The three cleared warnings are the CIMC placement rows.

  **Why:** a pre-flight check that warns about a correct design trains the
  operator to ignore warnings, which is worse than having no check. The fix
  belonged in the model, not in the check's thresholds.

  **Refs:** `schemas/nd-cluster.schema.json`, `shared/lib/inventory.py`,
  `automation/scripts/precheck.py`, lab decisions D-008 and D-011 in
  `~/.cursor/skills/rtp-b4-dmz-lab/SKILL.md`.

### Added

- **`scripts/install_secondaries.py` — re-image ND-2/ND-3 in parallel.** New
  Python orchestrator that drives the same Phase 1–4 install flow as
  `install_node1.py` (Redfish vMedia mount, UEFI vDVD one-time boot, SOL
  installer-skip, wait for installer completion, post-install power-on) but
  intentionally **omits Phase 5** (the first-boot SOL dialog) — that step is
  driven by ND-1's cluster orchestrator at stage `Setup boot time
  configuration` once cluster commit is accepted. Runs both secondaries
  concurrently with per-node state files (`state/node2.json`,
  `state/node3.json`) for full idempotency and resumability. Empirically the
  installer skip prompt appears 4–7 minutes after a force-restart, so the
  skip-wait timeout is set to 900 s (the original 120 s caused the script to
  silently assume the prompt had already passed and proceed to the
  install-complete wait, where it would stall indefinitely against a box
  that never got the `skip` command). See decision
  [D-012](#d-012--secondaries-must-match-cluster-leader-os-release-acs-reboot-factory-reset-preserves-the-os-image).
  - **Why.** During the 4.2.1.10 build, the cluster commit failed at stage
    `Setup boot time configuration` with the error `Node CIMC error response:
    The installed firmware version is incompatible with cluster's. [Node:
    4.1.1g. Cluster: 4.2.1.10]`. The two secondaries had been left over from
    an earlier 4.1.x lab build, and `acs reboot factory-reset` (our standard
    recovery primitive per [D-003](#d-003--recovery-primary-is-acs-reboot-factory-reset-not-full-re-image))
    *preserves the OS image*. So factory-reset alone could not reconcile the
    version drift; the only path was re-image. We did this once by hand at
    ~3 hours total (parallel) and codified the recipe so the next pod with
    this drift can run a single command instead of a multi-step procedure.
  - **Refs.**
    [`automation/scripts/install_secondaries.py`](automation/scripts/install_secondaries.py),
    [`automation/docs/troubleshooting.md` §17](automation/docs/troubleshooting.md#17-secondary-node-firmware-version-mismatch-blocks-cluster-commit),
    [`automation/RESUME.md` Scenario C](automation/RESUME.md#scenario-c--mid-build-secondary-re-image).

- **`precheck.py` — new `version.*` category.** Adds three rows
  (`version.iso_parse`, `version.node.<host>`, `version.cluster_match`) that
  parse the expected ND release from `cluster.iso.url`, SSH each node's mgmt
  IP and probe for the installed release using a **dual-form CLI fallback**
  (`acs version` for 4.2.x; `acs show version` for 4.1.x and earlier — the
  CLI was renamed at the 4.2 train), and FAIL if any drift is detected
  across nodes (WARN if all match each other but differ from the ISO
  baseline). The dual-form probe is the actually-relevant case for the
  upgrade scenario — during a migration window you may have mixed-release
  nodes where some answer one CLI shape and some the other; the precheck
  has to read both to detect drift between them. Detail strings annotate
  the legacy form with `(legacy CLI)` so operators can spot pre-4.2 nodes
  in the output. Pre-bootstrap (no mgmt IP yet) the per-node rows SKIP
  cleanly and the aggregate row surfaces operator guidance pointing at
  `install_secondaries.py`.
  - **Why.** The version-drift failure mode is the most expensive failure we
    hit in the 4.2.1.10 build (~3 h re-image + ~30 min ND-1 cleanup cycle).
    A 30-second precheck catches it before the maintenance window starts.
    The SSH-rescue-user model (vs. e.g. Redfish) is the only one that works:
    no Redfish field reports "what ND release is installed on the local
    disk", and the only first-class ND-side signal (`acs version`, formerly
    miscalled `acs show version` in our docs — see Fixed below) requires the
    OS to be booted and reachable on its mgmt IP. That's the actually-
    relevant moment, since cluster commit only happens after that anyway.
  - **Refs.**
    [`automation/scripts/precheck.py`](automation/scripts/precheck.py)
    (`check_node_os_version_match`, `_iso_version_from_url`,
    `_ssh_acs_version`),
    [`automation/docs/precheck-checklist.md` §A + §B.8](automation/docs/precheck-checklist.md),
    [`automation/docs/troubleshooting.md` §17](automation/docs/troubleshooting.md#17-secondary-node-firmware-version-mismatch-blocks-cluster-commit),
    decision [D-012](#d-012--secondaries-must-match-cluster-leader-os-release-acs-reboot-factory-reset-preserves-the-os-image).

- **MOP — new `Procedure 2 - Image remaining ND cluster nodes (conditional)`
  closes a documentation gap inherited from the original CVD.** The Cisco
  AI POD CVD ND chapter has only two procedures (deploy first node, then
  cluster bringup wizard) and never describes how the OS reaches ND-2 / ND-3.
  In the **factory-fresh** case (no prior ND OS on disk), the cluster-
  bringup wizard installs the ND OS on each secondary as part of cluster
  commit and the CVD's silent assumption holds. In the **brownfield** case
  (re-used hardware with any prior ND release on disk), cluster commit
  fails at `Setup boot time configuration` with `installed firmware
  version is incompatible` because ND-1 will not overwrite an existing OS
  — exactly the failure mode that bit us in the 4.2.1.10 build (we got
  lucky in that the failure surfaced loudly with a recoverable error;
  a customer following the CVD literally would crash at the same spot
  with no documented recovery). The new procedure adds an explicit
  `When to run this procedure` table that branches on hardware state and
  walks the operator through either `(A)` repeating Procedure 1 steps
  1-9 manually for each secondary, or `(B)` running the parallel
  `install_secondaries.py` automation. Then Procedure 2's validation
  step points at `precheck.py --category version` so the operator
  confirms uniformity *before* cluster commit. The MOP's downstream
  numbering shifts: `Procedure 2 → Procedure 3` (cluster bringup
  wizard), `§5 → §6` (Post-install), `§6 → §7` (Rollback and recovery,
  with `§6.1 → §7.1` for `acs reboot factory-reset`), `§7 → §8`
  (Validation checklist).
  - **Why.** Direct customer ask after observing that the existing CVD
    "got lucky" with their brownfield hardware. The 4.1.x physical-
    appliance Cisco deployment guide carries the underlying same-release
    requirement ("ensure that all nodes are running the same release
    version image"); this MOP procedure operationalises it for the
    AI POD CVD audience.

    [`docs/MOP-ND4-install.md` § 4](docs/MOP-ND4-install.md) (new
    Procedure 2 with §4.1 *When to run*, §4.2 *Two paths*, §4.3

- **`precheck.py` — three new guard rails closing the war-story → automation
  gap audit (gaps 1+2+4 in the audit) plus a fourth best-effort heuristic
  (gap 3).** Each is a direct translation of a lesson learned in the
  4.2.1.10 build into a check that fires *before* the operator hits
  the failure mode in the install path.
  - **`network.cimc_tcp_22.<host>`** — Cisco's [ND 4.2.x prerequisites](https://www.cisco.com/c/en/us/td/docs/dcn/nd/4x/deployment/42x/cisco-nexus-dashboard-deployment-guide-42x/m-prerequisites.html)
    explicitly mandate **both** TCP/22 and TCP/443 from the mgmt network
    to every CIMC. We previously only checked 443. Trivial parallel to
    `check_cimc_tcp_443`.
  - **`network.nd1_to_cimc.<host>`** — leader-vantage probe. After ND-1
    has its mgmt IP (post-Phase-5), SSH `rescue-user@nd-1` and `ping -c 2 -W 2`
    each secondary's CIMC over the default-routing path. This is the
    actual L3 path cluster-commit pre-flight uses (ND-1 bond1 → CIMC),
    which is L3-distinct from the workstation→CIMC path the existing
    `network.cimc_tcp_*` checks exercise. Catches the D-008/D-011
    failure mode ~30 s after Phase 5 completes, instead of mid-commit
    at stage `Setup boot time configuration`. **Why.** In the 4.2.1.10
    build, workstation→CIMC reachability passing was misleading — it
    didn't catch that ND-MGMT couldn't route to the original CIMC VLAN
    across the tenant↔lab firewall, and the failure surfaced ~3 h into
    the install as a cryptic "Node CIMC/Mgmt IP X is not reachable" 500
    on `POST /v2/bootstrap/cluster`. Cross-references
    `troubleshooting §14 + §16`
    and decisions [D-008](#d-008--when-cimcs-live-on-the-data-subnet-the-lab-must-route-mgmt-vlan--data-vlan)
    + [D-011](#d-011--cimcs-live-on-the-lab-oob-mgmt-vlan-to-keep-cluster-commit-pre-flight-on-a-single-lab-vrf-path).
  - **`network.nd1_data_to_gw`** — leader-vantage probe of bond0 → data
    gateway. Partial signal for STP Bridge Assurance Inconsistent (BA_Inc)
    on the data VLAN (the `troubleshooting §3`
    failure mode where the ND data port is `port type network` instead of
    `port type edge`). Acknowledged limitation: gateway might be reachable
    in some BA_Inc edge cases while inter-node data-plane is broken, so
    the §B switch-side `sh spanning-tree` capture remains the
    authoritative check; this is the only signal we can capture without
    switch-side access.

## Decisions

Architectural decisions that shape this section. Each is a separate item
with the trade-offs explicit. Prefer adding a new decision over editing
an old one — if a decision changes, mark it superseded and link the new
one.

### D-001 — Single source of truth for troubleshooting is `automation/docs/troubleshooting.md`

- **Date.** 2026-04-25
- **Status.** Accepted
- **Context.** We had troubleshooting hints in 3 places (section README,
  automation README, MOP rollback table). Each diverged from the others
  during the 4.2.1.10 build.
- **Decision.** All troubleshooting content lives in
  `automation/docs/troubleshooting.md`. Other docs link to numbered
  sections there rather than duplicating content.
- **Consequences.** (+) One place to update. (+) Cross-links from MOP,
  READMEs, script docstrings all converge. (–) The troubleshooting doc
  itself grows monotonically; we may need to split it eventually.

### D-002 — Wizard flow is verify-only by default; `--commit` is opt-in

- **Date.** 2026-04-25
- **Status.** Accepted
- **Context.** Once `POST /v2/bootstrap/persona` accepts a payload, ND
  creates a "draft" cluster record with no REST API to delete it. A
  subsequent commit attempt returns `500 Pending cluster bootstrap
  exists`. The only fix is `acs reboot factory-reset`.
- **Decision.** `wizard_flow_retry.py` runs steps 1–4 (status + 3
  verifies) by default. Steps 5–6 (persona + cluster commit) require
  `--commit`. The script's docstring documents this as a safety
  contract.
- **Consequences.** (+) Probing the API for syntax errors no longer
  bricks the cluster bootstrap. (–) An operator who forgets `--commit`
  will think the install is hanging when in fact verify ran and stopped.
  Mitigated by the script printing a clear "ran in verify-only mode;
  pass --commit to write state" footer.

### D-003 — Recovery primary is `acs reboot factory-reset`, not full re-image

- **Date.** 2026-04-25
- **Status.** Accepted
- **Context.** The pending-bootstrap deadlock has no API solution. The
  obvious fallback (re-image via CIMC ISO) costs ~3 h per node.
- **Decision.** `acs reboot factory-reset` is the documented and
  automated recovery primitive. It wipes only bootstrap config, preserves
  the OS install, completes in ~5 min, and returns the node to the
  first-boot dialog — at which point the orchestrator can re-drive only
  Phase 5 via the `state/node1.json` edit pattern.
- **Consequences.** (+) Recovery is ~36× faster. (+) Same SOL flow handles
  both fresh-install and post-reset paths with no code changes. (–) If
  the OS install itself is corrupted, `factory-reset` won't help; you
  must fall back to ISO re-image. The MOP rollback table covers both.

### D-004 — Secrets via env vars sourced from a secret manager; never inline

- **Date.** 2026-04-25
- **Status.** Accepted (lab pattern: macOS Keychain; production pattern:
  HashiCorp Vault or equivalent)
- **Context.** We discovered the literal lab CIMC password embedded in a
  cheatsheet markdown file. Beyond the workspace rule, this is a
  recurrence risk anywhere docs and code commingle.
- **Decision.** Secrets are referenced by `pass_ref` in inventory; the
  reference names an env var; the env var is populated per-shell from the
  secret manager via `security find-generic-password ...` (lab) or
  `vault kv get -field=...` (prod). The codebase touches the value only
  through `shared/lib/secrets.resolve()`. Future Vault swap is a
  one-file change.
- **Consequences.** (+) No literal credential in any tracked file.
  (+) Per-shell scope keeps the secret out of `.bash_history` if you
  unset after the run. (–) Operators must remember to populate the
  shell each time. Mitigated by RESUME.md's runnable snippets and the
  precheck `secrets.<env-var>` checks that fail loudly when a var is
  missing.

### D-006 — SOL peek-with-nudge is the primary diagnostic for "what is the box showing right now?"

- **Date.** 2026-04-25
- **Status.** Accepted
- **Context.** During the 4.2.1.10 build we repeatedly defaulted to "ask
  the operator to KVM in and tell us what's on screen" when SOL appeared
  silent. SOL only forwards live console bytes; quiescent prompts don't
  retransmit, which made SOL look unhelpful. Asking a human costs minutes
  to hours; SOL-with-nudge costs ~12 seconds and is scriptable.
- **Decision.** Operators and automation use
  `python scripts/main.py tail-sol --node ND-x --seconds 12` (or the
  inline 25-line snippet documented in
  [`automation/docs/troubleshooting.md` §11](automation/docs/troubleshooting.md#11-sol-peek-with-nudge-as-programmatic-state-source))
  as the first move when they need to know box state. KVM is reserved for
  cases where SOL is genuinely unavailable (CIMC reachability lost, etc.).
- **Consequences.** (+) Faster diagnostics, no human-in-the-loop blockers
  for state inspection. (+) Captured output is grep-able and goes into a
  log file, so we can correlate to other events. (–) The nudge has a
  caveat — strictly-validating prompts treat empty input as an answer and
  emit a validator error. Mitigated by `--no-nudge` and by the structural
  rule in `bootstrap_first_primary` (don't nudge after the password
  step). See decision rationale embedded in
  [`automation/docs/troubleshooting.md` §13](automation/docs/troubleshooting.md#13-do-not-nudge-at-strictly-validating-prompts).

### D-007 — ND 4.2.x first-boot dialog is intentionally minimal; full config goes via API

- **Date.** 2026-04-25
- **Status.** Accepted (this is a Cisco design choice; we record how we
  treat it, not whether we agree)
- **Context.** The console first-boot dialog on ND 4.2.1.10 asks for
  exactly five fields: admin password ×2, IP/mask, gateway, confirmation.
  Older ND minors and some CVDs document additional console prompts (DNS,
  NTP, hostname, search domain, timezone). Those prompts are absent in
  4.2.1.10; the corresponding fields are configured via the wizard or
  `POST /v2/bootstrap/cluster` after the box is reachable on its mgmt IP.
- **Decision.** `sol_bootstrap.py::bootstrap_first_primary` drives only
  the five prompts that 4.2.1.10 actually shows. All other config (DNS,
  NTP, hostname, search domain, timezone, persistent IPs, internal pod /
  service CIDRs, app/service installs) is owned by the cluster phase
  (`cluster_bringup.py` + `wizard_flow_retry.py`) and travels in the
  `POST /v2/bootstrap/cluster` payload. If a future ND minor adds console
  prompts, the SOL flow must be updated as part of that minor's qual.
- **Consequences.** (+) Sharp separation between "make the box reachable"
  (SOL) and "configure the cluster" (API). (+) All config except the
  reachability minimum is in declarative inventory, not in serial-driving
  code. (–) Operators looking at the SOL flow alone can't see how the
  cluster is actually configured; they need to read both the SOL flow
  and the cluster bringup. The `bootstrap_first_primary` docstring
  cross-references this.

### D-008 — When CIMCs live on the data subnet, the lab MUST route mgmt VLAN → data VLAN

- **Date.** 2026-04-25
- **Status.** Accepted (operator-side prereq, codified after empirical hit)
- **Context.** Cisco's reference ND deployment assumes the cluster leader can
  reach all node CIMCs from its mgmt interface. In our pod the CIMCs are
  cabled to the data subnet (`198.18.0.7/8/9`), and the mgmt-VLAN gateway
  (`192.0.2.254`) had no route to `198.18.0.0/24`. ND-1 holds its data
  interface (`bond0`) down until cluster commit pre-flight succeeds — and
  pre-flight needs CIMC reachability — so we deadlocked: cluster commit
  failed with `Node CIMC/Mgmt IP 198.18.0.8 is not reachable` before
  `bond0` could ever come up.
- **Decision.** When the lab places CIMCs on the data subnet (rather than the
  mgmt subnet), the lab admin must add a static route on the mgmt-VLAN
  gateway for the data subnet, next-hop being the L3 device that already
  serves both prefixes. The MOP §1 prereqs and `precheck.py` (eventually)
  must enforce a 5-row reachability matrix from inside ND-1 (mgmt GW, data
  GW, all 3 CIMCs) before any state-writing API call. The architectural
  alternative — re-IP CIMCs onto the mgmt subnet — is acceptable but
  carries higher operational cost (3 CIMC re-IPs + DNS + monitoring
  updates) and is treated as a future-work item, not the default fix.
- **Consequences.** (+) Captures a real prereq that bit us, with both a
  short-path fix (one route entry) and a long-path alternative. (+) Future
  pods that copy this lab can be checked against the ping matrix before
  bringup. (–) Today's `precheck.py` runs from the workstation, which
  reaches the data subnet via a campus VPN and therefore *can't* detect
  this gap. We need an in-ND-1 variant of the check; tracked as a TODO in
  the lab-admin request doc.

  Original text retained below for traceability. The decision was deliberated
  and partially executed (switch port flips for CIMC `M` interfaces were
  scheduled and started) before being abandoned mid-execution: flipping the
  CIMC `M` access port to VLAN 4 *before* changing the CIMC IP stranded each
  CIMC on the wrong VLAN, and an alternative (Lab OOB-MGMT, see D-011) became
  available which required no port flip and no FW rule change. No code or
  doc artifact was ever released against this decision. **Original status was:**
  Accepted (supersedes the implicit posture in D-008's "architectural
  alternative" — D-008 itself remains accepted as the *general-case* prereq for
  pods that *can't* take this path)
- **Context.** D-008 codified the rule "if CIMCs live on the data subnet, the
  lab MUST route mgmt VLAN → data VLAN." In our pod, the practical realization
  of that prereq turned out to require **inter-VRF route-leak plus firewall
  rule changes** (the CIMC subnet `198.18.0.0/24` lived in a different VRF
  from ND-MGMT `192.0.2.0/24`, with a FW between). The lab network team
  confirmed this was multi-team, multi-week work. Cluster commit was blocked
  in the meantime.
- **Decision.** Re-IP all 3 CIMCs from the CIMC VLAN onto the **ND-MGMT VLAN**
  (`192.0.2.77/78/79`). ND-1 then reaches every CIMC at L2 over `bond1` —
  no inter-VLAN routing of any kind needed at cluster commit pre-flight.
  This becomes the default deployment posture in MOP §1; D-008's L3 path is
  retained as a fallback for pods where re-IP is blocked by external
  constraints (e.g. CIMCs cabled to a fabric the deployment team doesn't own).
  Lab-side prerequisite: the access port carrying each CIMC `M` RJ-45
  must be in the ND-MGMT VLAN. If it isn't, that port flip is part of this
  change.
- **Consequences.** (+) Cluster commit pre-flight has zero L3 dependency on
  external routing or FW state. (+) Matches Cisco's reference posture for
  ND deployments. (+) Single-team change (chassis admin + IP owner only).
  (–) Operationally costs 3 CIMC re-IPs and (in some pods) a switch port
  VLAN move. (–) Future-pod operators inheriting CIMCs on a different VLAN
  must do this work or fall back to D-008's L3 path before bringup.
- **Refs.** [`automation/docs/troubleshooting.md` §14 Path A](automation/docs/troubleshooting.md#14-cluster-commit-fails-because-mgmt-vlan-cant-route-to-cimcs-on-another-vlan),
  [`docs/MOP-ND4-install.md` §1 + §2.2](docs/MOP-ND4-install.md),
  `automation/docs/lab-admin-request-mgmt-to-data-routing.md`
  (superseded; retained for the L3 path).

### D-010 — Never allocate an IP without explicit lab-owner approval

- **Date.** 2026-04-25
- **Status.** Accepted (operator + automation discipline)
- **Context.** While planning the CIMC re-IP under D-009, the agent proposed
  candidate IPs `192.0.2.107/108/109` based on inference ("looks visually
  grouped, away from the host range, away from the gateway"). The subnet owner
  immediately corrected to `192.0.2.77/78/79` — their actual reserved range for
  this purpose. Inference-based allocation, even when it doesn't collide today,
  has no reservation guarantee against future use of the same address by
  someone else, and silently breaks ND if reclaimed.
- **Decision.** Any IP the automation or operator needs — CIMC, persistent IP
  pool entry, future ND node, externally-exposed VIP, future automation address
  — is sourced via an **explicit request to the subnet/lab owner** before being
  written to any tracked file. The request includes: prefix, count needed,
  purpose, proposed labels, and any adjacency constraints. Approval is recorded
  in CHANGELOG under the change that consumes the IPs. `ping`/`arp` evidence
  that an address is currently unused is not approval.
- **Consequences.** (+) IPs in tracked files always correspond to lab
  reservations, not snapshots. (+) Eliminates a class of "worked when deployed,
  broken six months later" failures. (–) Adds a synchronous human dependency
  to any IP-allocating change. Mitigated by batching requests (ask once for a
  range, then assign within it).
- **Refs.** [`automation/docs/troubleshooting.md` §15](automation/docs/troubleshooting.md#15-never-allocate-an-ip-without-lab-owner-approval).

### D-011 — CIMCs live on the Lab OOB-MGMT VLAN, to keep cluster commit pre-flight on a single lab-VRF path

- **Date.** 2026-04-27
- **Status.** Accepted. Supersedes [D-009](#d-009--cimcs-live-on-the-nd-mgmt-vlan-superseded-by-d-011).
  D-008 remains accepted as the *general-case* fallback (when re-IP onto a
  routable lab segment is blocked by external constraints).
- **Context.** D-008 codified "if CIMCs live on the data/tenant VLAN, the lab
  must route ND-MGMT → that VLAN". In our pod, that L3 path crossed a
  tenant-VRF ↔ lab-VRF firewall boundary that required FW rule changes the lab
  network team confirmed were multi-team. D-009 then proposed co-locating the
  CIMCs on ND-MGMT itself (`192.0.2.77/78/79`) to make ND-1 ↔ CIMC L2-adjacent.
  D-009 was attempted, but the operational sequence (flip the CIMC `M` access
  port to VLAN 4, then change CIMC IP) had a sharp ordering hazard: flipping
  the port first stranded each CIMC on the wrong VLAN with no remaining IP
  path. While we were considering whether to revert ports and retry the
  IP-first ordering, the subnet owner pointed out that **Lab OOB-MGMT VLAN 10
  (`198.51.100.0/24`) and ND-MGMT VLAN 4 (`192.0.2.0/24`) are in the same lab
  VRF and route to each other through a pre-permitted lab firewall** (this
  pod's CIMC `M` ports were already cabled to VLAN 10). That removed every
  cost line item that was making D-009 expensive: no port flip, no FW rule
  change, no inter-VRF traversal. We verified ND-1 (192.0.2.7) reaches
  198.51.100.124/125 (Lab OOB NTP servers as known-reachable witnesses) before
  asking for any IPs; see
  `automation/logs/lab-ib-oob-routing-verify-20260427T123154Z.log`.
- **Decision.** Re-IP all 3 CIMCs from the original tenant CIMC VLAN
  (`198.18.0.7/8/9`) onto the **Lab OOB-MGMT VLAN** at
  `198.51.100.87/88/89` (allocation approved by the subnet owner per D-010 —
  this was a fresh request because the prior `.77/.78/.79` reservation under
  D-009 was on a different subnet entirely). At cluster-commit pre-flight
  ND-1 reaches every CIMC over a single lab-VRF L3 hop through a pre-permitted
  FW. This becomes the default deployment posture for any pod where the lab
  has the same IB-MGMT/OOB-MGMT structure; the principle (single lab-owned L3
  path, no tenant-VRF or FW-rule dependency) is what generalizes, not the
  specific subnets. D-008's L3 path is retained as the fallback for pods
  where re-IP is blocked by external constraints (e.g. CIMCs cabled to a
  fabric the deployment team doesn't own).
- **Consequences.**
  - (+) Cluster commit pre-flight has zero dependency on tenant-VRF state or
    on tenant↔lab FW policy; any change in tenant networking is decoupled
    from ND-1's ability to reach the CIMCs.
  - (+) No switch port VLAN move required for this pod; the order-of-operations
    hazard that bit D-009 doesn't exist on this path.
  - (+) Single-team change (chassis admin + Lab OOB subnet owner only).
  - (+) Topology rationale generalizes (the recipe — "put CIMCs where ND-MGMT
    reaches them through a single lab-owned L3 path" — is captured in MOP §1
    and troubleshooting §16 in topology-neutral form).
  - (−) Path traverses a permissive FW with ~1 Gbps capacity. CIMC mgmt
    traffic at cluster-commit pre-flight is a few `ping`/HTTPS connections,
    well under any sustained capacity concern, but worth noting for future
    bulk operations (e.g. simultaneous Redfish firmware pulls across many
    chassis).
  - (−) Future pods that *don't* have the lab IB-MGMT/OOB-MGMT structure
    can't copy this exact placement; they must apply the principle and pick
    a segment with the same property in their topology, or fall back to D-008.
- **Refs.** [`automation/docs/troubleshooting.md` §14 Path A + §16](automation/docs/troubleshooting.md#14-cluster-commit-fails-because-mgmt-vlan-cant-route-to-cimcs-on-another-vlan),
  [`docs/MOP-ND4-install.md` §1 + §2.2](docs/MOP-ND4-install.md),
  `automation/inventory/nodes.yaml`,
  `automation/logs/bootstrap-final-payload.json`,
  `automation/logs/lab-ib-oob-routing-verify-20260427T123154Z.log`.

### D-012 — Secondaries must match cluster-leader OS release; `acs reboot factory-reset` preserves the OS image

- **Date.** 2026-04-28
- **Status.** Accepted (operator + automation discipline; codifies a hard
  prerequisite that bit us late in the 4.2.1.10 build)
- **Context.** During the 4.2.1.10 cluster commit, ND-1 accepted the persona
  payload and the cluster commit, then failed at stage `Setup boot time
  configuration` with:

  ```
  Node CIMC error response: The installed firmware version is incompatible
  with cluster's. [Node: 4.1.1g. Cluster: 4.2.1.10]
  ```

  Both secondaries were physically the same chassis as the prior 4.1.x lab
  build and had `4.1.1g` on disk. Our standard recovery primitive —
  [D-003](#d-003--recovery-primary-is-acs-reboot-factory-reset-not-full-re-image)
  `acs reboot factory-reset` — explicitly **preserves the OS image**, so it
  could clear the bootstrap config but could not reconcile the version drift.
  The diagnosis path was painful: the symptom on the bringup-monitor looked
  like a generic "stuck at Setup boot time configuration", and only by
  reading the failed-cluster record's underlying error string (which the
  monitor truncated) did we discover the real cause. We diagnosed and
  re-imaged in-flight, costing ~3 h re-image (parallel) + ~30 min ND-1
  factory-reset + Phase 5 re-drive cycle.
- **Decision.**
  1. **Hard prerequisite.** All 3 nodes that will join the cluster MUST be
     on the same ND OS release as the cluster ISO before `POST
     /v2/bootstrap/cluster` is called. This is a stronger statement than
     "fresh state" — fresh state is necessary but not sufficient.
  2. **Recovery path** for stale secondaries is `scripts/install_secondaries.py`
     (re-image ND-2/ND-3 in parallel via Redfish vMedia + UEFI vDVD one-time
     boot, then let them land at the post-install fresh state for ND-1's
     orchestrator to pick up). The leader, if also stale, uses
     `scripts/install_node1.py`. Total parallel cost ~3 h vs. ~10 h serial.
  3. **Preflight detection** is `scripts/precheck.py --category version`,
     which SSHes `rescue-user` to each node's mgmt IP, runs `acs version`,
     and FAILs on any cross-node drift (the actual cluster-killer; absolute
     version mismatch with the ISO is WARN). This works only post-mgmt-IP,
     which is the actually-relevant moment — cluster commit only runs after
     all 3 are reachable on mgmt anyway.
  4. **Detection model rationale.** No Redfish/CIMC field reports "what ND
     release is installed on the local disk". The only first-class signal
     is `acs version` over SSH (rescue-user) once the OS has booted and
     answers on its mgmt IP. We considered a SOL-peek-for-banner approach
     (the installer prints the release at the end of Phase 3) but the SOL
     channel is single-reader and the install scripts already hold it
     during install windows; a separate observer would compete with the
     install. SSH is cheaper, more robust, and trivially parallelizable.
- **Consequences.**
  - (+) The most expensive failure mode in the 4.2.1.10 build is now
    detectable in <30 s of preflight, vs. ~3.5 h of in-flight diagnosis +
    recovery.
  - (+) The recovery itself is now a single command per affected node,
    not a multi-step procedure that has to be reconstructed from notes
    inside a maintenance window.
  - (+) `install_secondaries.py` is itself idempotent and resumable
    (per-node state files), so a paused or interrupted re-image can be
    picked up rather than restarted.
  - (−) The preflight check requires the mgmt IPs to already be answering
    SSH, so it can't catch the case where the operator hasn't yet bootstrapped
    any node — but that case is also when the operator can trivially run
    `install_secondaries.py` against fresh hardware as part of the install
    flow, so the gap is acceptable.
  - (−) Cisco's reference docs continue to call the relevant command
    `acs show version`, which doesn't work on 4.2.x. Our docs use `acs
    version` and call out the discrepancy in
    `troubleshooting.md` Appendix B
    so future operators don't waste time on the misnamed reference.
  - (−) **Cisco doc regression.** The "all nodes must be running the same
    release version image" warning was present in the [ND 4.1.x physical
    deployment guide](https://www.cisco.com/c/en/us/td/docs/dcn/nd/4x/deployment/cisco-nexus-dashboard-deployment-guide-41x/nd-deploy-physical-41x.html)
    and earlier 3.2.x guides, but is **absent** from the
    [ND 4.2.x deployment guide § Prerequisites and Guidelines](https://www.cisco.com/c/en/us/td/docs/dcn/nd/4x/deployment/42x/cisco-nexus-dashboard-deployment-guide-42x/m-prerequisites.html).
    The specific commit-time error string (`The installed firmware version
    is incompatible with cluster's. [Node: <X>. Cluster: <Y>]`) is also not
    indexed anywhere in Cisco's 4.2.x troubleshooting collateral. This is
    why the prerequisite is documented redundantly in our own stack
    ([`README.md` § Prerequisites > Software](README.md#software),
    `troubleshooting.md` §17, this decision, and `precheck.py --category
    version`) — we cannot rely on Cisco docs to surface it for the operator.
    If/when Cisco restores the warning in a future 4.2.x revision, drop
    the redundancy.
- **Refs.**
  [`automation/scripts/install_secondaries.py`](automation/scripts/install_secondaries.py),
  [`automation/scripts/precheck.py`](automation/scripts/precheck.py)
  (`check_node_os_version_match`),
  [`automation/docs/troubleshooting.md` §17](automation/docs/troubleshooting.md#17-secondary-node-firmware-version-mismatch-blocks-cluster-commit),

### D-005 — Changelog is updated in the same change as the code/doc it describes

- **Date.** 2026-04-25
- **Status.** Accepted
- **Context.** We've seen rationale-loss problems on prior projects when
  a "we'll write the changelog before release" habit accumulates a backlog
  the author can no longer reconstruct.
- **Decision.** Every PR / change touches CHANGELOG.md if it changes
  user-visible behavior, the operator surface, or the documentation. CI
  may eventually enforce this; for now it's an operator discipline.
- **Consequences.** (+) The "why" is captured while it's fresh. (–) Small
  PRs feel a bit heavier. Worth it.
