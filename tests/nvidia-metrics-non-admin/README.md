# NVIDIA GPU Metrics Test (non-admin)

Validates that non-admin (unprivileged, non-root) OpenShift workloads can
collect NVIDIA GPU profiling metrics — the same class of counters used by
`dcgm-exporter` (DCGM `DCGM_FI_PROF_*` fields) and by CUPTI-based tools
(`ncu`, `nsys`, PyTorch profiler).

This exercises the driver setting `NVreg_RestrictProfilingToAdminUsers=0`
(runtime name `RmProfilingAdminOnly`), applied to the NVIDIA GPU Operator via
a `kernelModuleConfig` ConfigMap. See
[docs/guide_troubleshooting.md](../../docs/guide_troubleshooting.md) or the
GPU Operator docs for background on that setting.

## What it does

A Kubernetes Job runs as a non-root, capability-dropped container
(`restricted-v2`-compatible SCC) and:

1. Reports the driver's `RmProfilingAdminOnly` value (informational).
2. Confirms the GPU is visible via `nvidia-smi`.
3. Starts an in-pod `nv-hostengine` and generates load with `dcgmproftester`.
4. Samples `DCGM_FI_PROF_*` fields via the DCGM Python bindings.
5. Runs Nsight Compute (`ncu`) against a small CUDA kernel to test CUPTI
   counter access directly — the most definitive check, since it fails with
   the explicit error `ERR_NVGPUCTRPERM` if profiling is still admin-only.

## Prerequisites

- `oc` CLI logged in to the target cluster (`oc login` / `oc whoami`).
- A namespace you can create Jobs, BuildConfigs, and ImageStreams in.
- At least one schedulable node with `nvidia.com/gpu` allocatable.
- Python 3.9+ on the machine running `setup.py` (only used to shell out to
  `oc`; no extra Python packages required).

## Step 1: Confirm the internal image registry is usable

The build pushes the test image to the cluster's internal registry. Check it
first:

```bash
oc get configs.imageregistry.operator.openshift.io/cluster \
  -o jsonpath='{.spec.managementState}{"\n"}'
```

- **`Managed`** — you're ready, skip to Step 2.
- **`Removed`** or the command errors — the registry isn't running. This is
  common on bare-metal/on-prem clusters where the installer had no default
  storage class to pick.

To enable it, you need a `ReadWriteMany`-capable storage class (for example,
a Portworx `sharedv4` file class). Find one:

```bash
oc get storageclass
```

Then let `setup.py` provision the PVC and patch the registry operator for
you (see Step 3 for the full invocation):

```bash
python3 setup.py --namespace <your-namespace> \
  --enable-registry --storage-class <your-rwx-storage-class>
```

This is a **cluster-wide, admin-level change** — it affects every user of the
internal registry, not just this test. Confirm with your cluster admin
before running it on a shared cluster. It:

1. Creates a 200Gi RWX PVC named `image-registry-storage` in
   `openshift-image-registry`.
2. Patches the registry operator to `managementState: Managed`, using that
   PVC, with a route exposed.

If you'd rather do this by hand, see
[openshift/image-registry-pvc.yaml.tmpl](openshift/image-registry-pvc.yaml.tmpl) and:

```bash
oc patch configs.imageregistry.operator.openshift.io/cluster --type=merge -p '{
  "spec": {
    "managementState": "Managed",
    "storage": {"pvc": {"claim": "image-registry-storage"}}
  }
}'
```

## Step 2: Pick a namespace

Any namespace where you can create Jobs, BuildConfigs, and ImageStreams
works. `setup.py` defaults to your current `oc project` if `--namespace` is
omitted.

## Step 3: Build the image and run the test

```bash
cd tests/nvidia-metrics-non-admin
python3 setup.py --namespace <your-namespace>
```

This will:

1. Verify `oc` is logged in.
2. Check the registry (see Step 1 — pass `--enable-registry` if needed).
3. Create a BuildConfig/ImageStream (if one doesn't already exist) and run
   `oc start-build --from-dir=image --follow`.
4. Render [openshift/job.yaml.tmpl](openshift/job.yaml.tmpl) for your
   namespace into `openshift/job.rendered.yaml`.
5. Delete any prior `gpu-metrics-test` Job and create the new one.
6. Tail the Job's logs until it completes.

### Useful flags

| Flag | Purpose |
|---|---|
| `--namespace NAME` | Target namespace (default: current `oc project`) |
| `--node NAME` | Pin the Job to a specific node (`kubernetes.io/hostname`) — useful when you just changed a driver setting on one specific GPU node |
| `--skip-build` | Reuse the existing `gpu-metrics-test:latest` image instead of rebuilding |
| `--enable-registry` | Provision the registry PVC and enable the operator (requires `--storage-class`) |
| `--storage-class NAME` | RWX storage class for the registry PVC |
| `--no-follow` | Create the Job but don't tail its logs |

### Example: pin to the node you just updated

```bash
python3 setup.py --namespace my-namespace --node gpu-worker-03
```

## Interpreting the results

The Job log ends with a `Result` section: `ALL CHECKS PASSED` or `ONE OR
MORE CHECKS FAILED`. The two checks that answer "can non-admin users collect
GPU metrics" are:

- **`Sampling profiling fields`** — DCGM `DCGM_FI_PROF_*` values are
  non-blank/non-zero (the `dcgm-exporter` path).
- **`CUPTI kernel profiling (Nsight Compute) as non-root`** — `ncu`
  successfully profiled the test kernel without hitting `ERR_NVGPUCTRPERM`
  (the CUPTI/Nsight/PyTorch-profiler path).

If either fails, check on the node itself:

```bash
oc debug node/<gpu-node> -- chroot /host cat /proc/driver/nvidia/params \
  | grep -i RmProfilingAdminOnly
```

It must read `RmProfilingAdminOnly: 0`. If it doesn't, the driver hasn't
picked up the `kernelModuleConfig` change yet — the driver DaemonSet pod on
that node needs to be deleted (which reloads the kernel module) or the node
rebooted if the module won't unload.

## Cleaning up

```bash
oc delete job gpu-metrics-test -n <your-namespace>
oc delete bc,is gpu-metrics-test -n <your-namespace>
```

## Rerunning after a change

Jobs are immutable; `setup.py` already deletes the prior Job before creating
a new one, so simply re-run it:

```bash
python3 setup.py --namespace <your-namespace> --skip-build
```
