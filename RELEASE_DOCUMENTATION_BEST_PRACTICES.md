# Release Documentation Best Practices

## Overview
This document outlines the recommended approach for managing release documentation in the Cisco AI PODs repository, using industry best practices from Ansible Galaxy and other enterprise projects.

## 📋 Release Documentation Structure

### 1. **Changelog Fragments** (Primary Source of Truth)
**Location:** `changelogs/fragments/`  
**Format:** YAML  
**Naming:** `<feature-name>-<version>.yml`

Changelog fragments are the **primary documentation** for each release. They follow Ansible Galaxy Changelog Plugin format and serve as the source material for generating the main CHANGELOG.

**Fragment Structure:**
```yaml
---
release_summary: |
  High-level summary of the release (1-2 sentences)

major_changes:
  - |
    Major feature or significant change with bullet points
  - |
    Can span multiple lines with pipe (|) continuation

features:
  - |
    New feature or capability added
  - |
    Implementation details and usage

bugfixes:
  - |
    Bug fix with description
  - |
    Root cause and resolution

known_issues:
  - |
    Known limitation or issue
  - |
    Workaround or future plan

documentation:
  - |
    New documentation or guides added
  - |
    Configuration examples

release_notes: |
  Additional release notes or migration guidance
```

**When to Create a Fragment:**
- For each significant release (minor or major version bump)
- Captures all changes in a structured format
- Becomes input for CHANGELOG.md generation

### 2. **CHANGELOG.md** (Generated, Not Hand-Edited)
**Location:** Repository root  
**Generated From:** `changelogs/changelog.yaml` and fragments  
**Update Method:** Auto-generated by Ansible Changelog Plugin

The main CHANGELOG.md is **auto-generated** from fragments and should NOT be hand-edited.

**Generation Process:**
```bash
# Using ansible-changelog plugin (if installed)
antsibull-changelog generate

# Or manually from fragments if needed
# This consolidates all fragments into CHANGELOG.md
```

**Example Structure:**
```markdown
## [0.1.16] - 2026-11-16

### Major Changes
- DNS Manager Framework with multi-provider support
- Web UI for DNS Manager page
...

### Features
- Multi-provider DNS support
...

### Bug Fixes
- Fixed LDAP configuration loading
...

### Known Issues
- OpenShift file detection requires ezai.yaml format
...
```

### 3. **RELEASE_v<version>.md** (Detailed Release Notes)
**Location:** Repository root  
**Format:** Markdown  
**Audience:** End users and customers  
**Purpose:** Comprehensive deployment guide and feature documentation

This is a **detailed, hand-crafted** document containing:
- Overview and key features
- Deployment instructions
- Configuration examples for each provider
- Troubleshooting guide
- Security best practices
- API documentation (if applicable)

**When to Create:**
- For each production release
- Detailed enough for customers to understand all features
- Includes migration/upgrade guidance
- Contains complete configuration examples

### 4. **DELIVERY_SUMMARY_<feature>.md** (Optional Project Artifacts)
**Location:** Repository root  
**Format:** Markdown  
**Purpose:** Internal project delivery summaries and decision logs

These are **optional** project tracking documents created during development to:
- Document architectural decisions
- Track implementation progress
- Record technical decisions and rationale
- Provide context for code reviewers

**When to Create:**
- During significant feature development
- Complex or multi-phase projects
- When decision documentation is needed
- As an artifact for stakeholder communication

**Note:** These should be created but are not part of the official release cycle. Keep them for historical reference but don't include in CHANGELOG fragments unless significant.

## 🔄 Release Documentation Workflow

### Step 1: Development Phase
Create technical summaries and decision logs as needed during development:
```bash
# Create detailed delivery summary (optional)
DELIVERY_SUMMARY_dns_manager.md

# Document architectural decisions
# Record implementation notes
```

### Step 2: Pre-Release Phase
Before tagging a release, create the changelog fragment:
```bash
# Create changelog fragment in /changelogs/fragments/
# File: dns-manager-v0.1.16.yml
# Contents: Structured YAML with all changes
```

**Fragment Example:**
```yaml
---
release_summary: DNS Manager v0.1.16 - Production-ready DNS record management

major_changes:
  - DNS Manager Framework with 5 provider types
  - Web UI DNS Manager page
  - Automatic record extraction

features:
  - Multi-provider DNS support
  - LDAP auto-configuration

bugfixes:
  - Fixed LDAP URL parsing
  - Fixed file detection

documentation:
  - Comprehensive release notes (see RELEASE_v0.1.16.md)
  - Customer deployment guide
```

### Step 3: Release Phase
Create the detailed release notes document and tag the release:
```bash
# Create detailed RELEASE_v0.1.16.md with:
# - Full feature descriptions
# - Configuration examples
# - Troubleshooting guide
# - Security best practices
# - Deployment checklist

# Tag the release
git tag -a v0.1.16 -m "Release v0.1.16 - DNS Manager with Production-Ready Schema"

# Push tag
git push origin v0.1.16
```

### Step 4: Post-Release
Generate or update CHANGELOG.md if using Ansible Changelog Plugin:
```bash
# If antsibull-changelog is available
antsibull-changelog generate

# Otherwise, CHANGELOG.md remains as historical record
# with manual v0.1.16 section added
```

## 📚 Documentation Types and Purposes

| File | Type | Audience | Purpose | Update Frequency |
|------|------|----------|---------|------------------|
| `changelogs/fragments/*.yml` | Structured | Developers | Source of truth for changes | Per release |
| `CHANGELOG.md` | Generated/Manual | Developers | Historical change log | Per release |
| `RELEASE_v*.md` | Detailed | Customers/Users | Complete deployment guide | Per release |
| `DELIVERY_SUMMARY_*.md` | Project Artifact | Project Team | Implementation tracking | As needed |

## ✅ Checklist for Release Documentation

Before tagging a release:

- [ ] **Changelog Fragment Created**
  - [ ] File in `changelogs/fragments/`
  - [ ] Named as `<feature>-<version>.yml`
  - [ ] Contains: release_summary, major_changes, features, bugfixes
  - [ ] All sections documented with pipe (|) for multi-line entries
  - [ ] YAML syntax valid

- [ ] **Detailed Release Notes Created**
  - [ ] File named `RELEASE_v<version>.md`
  - [ ] Contains: overview, key features, deployment instructions
  - [ ] Includes configuration examples for each provider/feature
  - [ ] Security best practices documented
  - [ ] Troubleshooting guide included
  - [ ] Deployment checklist provided

- [ ] **Git Tag Created**
  - [ ] Tag message includes changelog summary
  - [ ] Tag pushed to remote
  - [ ] Release notes available to customers

- [ ] **CHANGELOG.md Updated** (if applicable)
  - [ ] Manual or auto-generated from fragments
  - [ ] Latest version appears at top
  - [ ] All sections properly formatted

## 🎯 Best Practices Summary

### ✅ DO:
1. **Create changelog fragments** for every release - they're the source of truth
2. **Hand-craft detailed RELEASE_*.md** with deployment guides and examples
3. **Keep CHANGELOG.md generated** - don't hand-edit, regenerate from fragments
4. **Use structured YAML** in fragments with clear sections
5. **Document decisions** in DELIVERY_SUMMARY_*.md during development
6. **Tag releases** with comprehensive git commit messages
7. **Include examples** in release documentation - customers need them
8. **Keep historical records** - don't delete old release notes

### ❌ DON'T:
1. **Hand-edit CHANGELOG.md** directly - regenerate from fragments
2. **Mix multiple releases** in a single fragment file - one fragment per release
3. **Skip bugfixes section** - even if none, document as "No known issues"
4. **Forget security notes** - always include security best practices
5. **Leave fragments without** structured sections - consistency matters
6. **Delete old RELEASE_*.md files** - keep for version-specific guidance
7. **Tag without** comprehensive release notes - customers need context

## 🔗 Related Configuration

**changelogs/config.yaml** contains:
```yaml
---
title: Cisco AI PODs
notesdir: fragments
changelog_filename_template: ../CHANGELOG.md
```

This tells the changelog plugin:
- Project name: "Cisco AI PODs"
- Fragment directory: `changelogs/fragments/`
- Output: `CHANGELOG.md` in repo root

## Summary

The recommended approach uses:
1. **Changelog Fragments** (YAML) - Structured, source of truth
2. **CHANGELOG.md** (Auto-generated) - Main changelog
3. **RELEASE_v*.md** (Hand-crafted) - Customer-facing deployment guides
4. **DELIVERY_SUMMARY_*.md** (Optional) - Project tracking artifacts

This separation of concerns provides:
- **Maintainability**: Each document has a clear purpose
- **Automation**: CHANGELOG.md generated from structured fragments
- **Usability**: Detailed release notes for customers
- **History**: Complete record of all changes over time
- **Scalability**: Easy to add new releases following the pattern
